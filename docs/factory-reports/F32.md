## Design decisions

- **Reach is a separate collection.** Thumbnail reach is NEVER read
  from the per-video Analytics query — it uses the Reporting API
  `channel_reach_basic_a1` report with its own two metrics. Both the
  client and the fake transport reject unsupported combinations, so a
  regression to generic `ctr` fails loudly at the wire.
- **Coverage ≠ requested period.** `requested_period` is the
  theoretical horizon window (published→due); `actual_coverage` is
  derived from the day rows the API actually returned. Short coverage
  → `partial`; no rows → `pending`; route failure → `failed`/`partial`
  — never silently "0".
- **Retries are not samples.** One `MetricSnapshot` per
  (publication, horizon, query_version): delayed/OAuth retries UPDATE
  the same record with `attempts` incremented — verified that repeated
  pulls keep exactly one record.
- **Retention stays native.** `averageViewPercentage` (and any
  ratio metric) passes through unclamped — 120% means rewatches, not
  a bug.
- **Zero is measured, missing is unknown.** A measured-0 row set
  yields `metrics[name]=0` with `availability=ok`; absent data yields
  `None` plus a reason (`no_rows_yet`, `route_failed`,
  `metric_not_returned`). The legacy collapse to `0.0` exists ONLY in
  `compat.py`, which also carries `availability` through so consumers
  can see it.

## Open risks / manual verification

- The Reporting API job/report lifecycle is modelled as a direct
  report call; live enablement (M04) must confirm the account's actual
  report availability and whether a report job must be created first.
- `compare` is descriptive only — causal A/B claims belong to F33's
  decision policy, not here.
- Manual-import horizons are free-form (`horizon="manual"`); F33
  should treat them as observational evidence only.
